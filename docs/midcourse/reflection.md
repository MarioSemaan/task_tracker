# Reflection — Mid-Course Project

For this project I used GitHub Copilot in VS Code as my main AI assistant throughout for design decisions, code generation, test generation, and debugging. I used it in small, scoped steps rather than asking for the whole feature at once: first settling a design question (e.g. should `overdue` be stored or computed?), then implementing just that piece, then testing it, before moving to the next layer. This matched the workflow from the module — plan, implement, verify, refine rather than asking for everything in one shot.

One moment where AI genuinely helped was generating the pytest tests for both features. Once I gave it the existing fixture pattern (the `client`/`created_task` fixtures already in `tests/test_tasks.py`), it produced tests that fit naturally into the file instead of introducing a different testing style. It also proposed sensible edge cases I hadn't thought of on my own, like confirming that PATCHing tags doesn't affect unrelated fields like priority.

One moment where it slowed me down, or rather, where I had to actively correct it, was during test generation for the due-dates feature. The AI's first draft of the "Done tasks are never overdue" test assumed a task could move directly from ToDo to Done. But my actual `business_rules.py` only allows the sequential path: ToDo -> InProgress -> Done. If I'd run that test as originally written, it would have failed for the wrong reason not because the feature was broken, but because the test itself assumed a transition my backend doesn't allow. Catching this meant actually reading my own business rules file before trusting the generated test, rather than just running whatever was produced.

That moment is a good example of how reviewing the AI's output changed the actual result. If I'd blindly accepted the first draft, I would have either had a false test failure to debug, or worse, might have been tempted to loosen the business rule just to make the test pass which is exactly the kind of symptom-suppression the module warns against. Instead, I fixed the test to match the real, tested transition rule.

The habit I'll carry into later modules is treating every AI-generated test as a claim to verify, not a finished artifact checking it against the actual source behavior before running it, and always proving new tests with a deliberate Break Test rather than trusting a single green run.
